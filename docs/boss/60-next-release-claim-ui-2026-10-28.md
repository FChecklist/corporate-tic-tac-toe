## ADDED 2026-10-28 (owner principle): TINY-SIGNAL PROTOCOL for all phone <-> server talk
Owner: the app is already downloaded in the browser from the web link, so every later exchange must be minimum bits, so even a 2-3 s heartbeat costs almost nothing: saves data, time, and feels real time.
PLAN
1. Numbers need no server (phones compute them from the public beacon): keep that.
2. One tiny heartbeat per game: GET /api/z/<id>/hb returns a few bytes: a version number per topic (claims, game state pause/resume/end, roster/check-in counts for organizer). Phone compares with its own; equal = stop; higher = fetch only that topic's small delta once. Encoded as plain text digits (e.g. "17.3.52"), no JSON, gzip not needed.
3. Served from the Cloudflare cache (s-maxage 2-3 s, same for all phones of a game), the database is read only when something changes (version counter written with the real event).
4. Delta only: the follow-up fetch returns just events after the phone's version (claim lines: ticket, prize, state).
5. Adaptive rhythm: 2-3 s while a game is in play or a claim is pending; 10-30 s before start and after end; stop when the tab is hidden/locked, one catch-up call on return ('away and return'). Random jitter so 250 phones do not hit together.
6. Presses (claim, tap, check-in) stay as small POSTs with one reply; heartbeat never carries decisions: the server clock decides every claim as today.
7. Measure and publish: bytes per heartbeat, per phone per hour, requests per game per hour, delay from event to pop-up on a phone (target <= 4 s). Budget check against Cloudflare free limits BEFORE going live (250 phones x 1 call/3 s = ~300k calls/hour/game: must be answered from cache without waking the database; confirm how Pages Functions count cached hits, else slow to 5 s or use a static edge file).
8. Tests: version bumps once per event; equal version = no fetch; delta correct after a missed event; hidden tab sends nothing; 250-phone local load test; falsify each.
Release: with the claim buttons/timer/fast notice; not before Sneha's game.

## DECISION 2026-10-28 (owner): use the CHEAPER AND FASTER path for the heartbeat = STATIC EDGE FILE
- Heartbeat/version file per game, e.g. /hb/<gameId>.txt, a few bytes ("17.3.52"), served by Cloudflare as a static asset (not a Function): no function request, no database, answered at the nearest edge in tens of ms, cache 1-2 s.
- Server writes it only when something changes (claim, pause/resume, end, roster). Needs a way to publish an asset per game change: options to test in order: (a) Cache API entry written by the claim Function and read by a tiny route; (b) R2/KV object with short cache; (c) Function with s-maxage. Pick the one with measured lowest cost AND event-to-phone delay <= 2-3 s; phones poll every 2 s while playing.
- Real-time test target: claim pressed -> pop-up on other phones <= 3 s at p95 with 250 phones; request count and cost per game-hour recorded.
- Fall back to Function+cache only if the static route cannot be updated fast enough.
