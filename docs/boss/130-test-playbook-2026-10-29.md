# 130 - Test playbook: how Corporate Tambola was tested, and how to repeat it for the other games, DPDP and Townhall (29 Oct 2026)

Written by a read-only analyst pass. Nothing was run, nothing deployed. Every fact below comes from the memory notes and files named in it. Times and RAM figures marked (est.) are my estimates from the notes, not measurements.

## 1. Summary (5 lines)

1. Tambola was tested in seven layers: unit/page tests, rule steps at 1,000,000 checks, a local simulation stack, a 100-case campaign with node phones, click-only real-browser games (Chrome, Chromium, WebKit), live games on the real site, and load/scale plans. Each layer found different bugs.
2. The bugs that mattered most (employees-only reset, WebKit no control key, logo upload killing the form, Quick-setup demo locked) were found only by clicking like a person, never by API tests or unit tests.
3. Quality came from the method, not the volume: an audit with two skeptics per finding, "falsify every fix" (break it, see red, restore), and an owner-concern table with GREEN / RED / NOT TESTED per row.
4. Go-live is gated: no deploy near a live game, version.json must show the new commit, a live 10-player check with claim rows re-read from D1, and a rollback path. Honest limit: Tambola was never certified six sigma; only rule steps were.
5. Other games, DPDP and Townhall can reuse the tools below. Most mechanical layers need no AI judgement and can run cheaply; judgement is needed only for gap finding, wording and the go/no-go.

## 2. The testing layers Tambola went through (in order)

Where to run: CLOUD = can run in a cloud session with no secrets and no live services. LAPTOP = needs this laptop (real Chrome, local server, or the Cloudflare/D1 tokens in `C:\ct\ct\.env.local`, never print them). LIVE = touches the real site.
Rule for every heavy layer: take the lock first (`mkdir C:\ct\heavy.lock`, `rmdir` when done; protocol in `C:\ct\HEAVY_JOB_PROTOCOL.md`), only when free RAM is above 1.2 GB, one heavy job at a time, and never while a live game runs (see section 5).

### L1. Code tests (unit, edge, page tests)
- Purpose: every rule in code, every wording on a page, privacy and storage guards.
- Command (Tambola repo `C:\ct\test-sites\tambola`): `bun test` (edge suite in `apps/edge/test`, page tests in `apps/web/test`, beacon tests in `packages/beacon`). Gate catalogue: `docs/GATES.md` (each gate true only with a named passing test).
- Inputs: none. Pass: all green. Last recorded: about 2,703 pass with 2 known flaky/stale (notes 26 Oct); 1,793 edge in the 25 Oct run.
- Time: several minutes (est.). RAM: moderate, 1 GB (est.). Run tests one file group at a time when RAM is short.
- Where: CLOUD for the code tests (no live service); known load-flaky tests pass alone.
- Lesson: this layer alone never found the biggest bugs (they sat between steps).

### L2. Rule steps S1-S13 at 1,000,000 checks
- Purpose: pure rules (join decisions, who wins what, settings, no-PII record) against independent oracles.
- Tool: `tools/sigma-steps.mjs` (`bun run tools/sigma-steps.mjs <N>`), result `data/sigma-steps.json`. S10 (join over HTTP): `tools/browser-tests/sigma-http.mjs` (`node tools/sigma-http.mjs 1000000 64` against a fresh local server on port 8802, `DAILY_WRITE_BUDGET` huge, limited stranger pools).
- Pass: 0 defects, and a negative control proves the checker CAN fail (1M join decisions, 0 wrong, cloud session note 26 Oct).
- Time: minutes for S1-S13; hours for S10 (est.). RAM: low to moderate. Where: CLOUD for the pure rule steps; S10 needs a local server (CLOUD possible, it ran in a cloud session).
- Lesson: first S10 run gave false "wrong" answers (a full game correctly returned 409); fix the test, not the product.

### L3. Local simulation stack (sim2) with virtual time
- Purpose: run the exact worker code on a copy of the live database without touching live.
- Tool: `tools/sim2/` (README in that folder). Commands from the repo: `node tools/sim2/parity.mjs` (schema and built files vs live), `bun tools/sim2/import-live.ts`, `bun tools/sim2/server.ts`, `node tools/sim2/smoke.mjs` (35 checks, about 1.5 min), `bun tools/sim2/crowd.ts '{...}'`.

- Time: the full ui run about 30 min per game; use `--only`. RAM: heavy with Chrome. Where: LAPTOP for ui (real Chrome); CLOUD for life/matrix (no browser).

### L4. 100-case campaign with node phones

- Time: hours (est.). RAM: heavy on laptop; the cloud box ran the big shards. Where: CLOUD for local-server runs (a cloud session did the 45-game 250/500/1000 mix), LAPTOP for quiet timing.

## 3. The audit method

1. **Owner-concern table.** Take the customer's/owner's real words and turn each into a numbered row with a verdict GREEN / RED / PARTIAL / NOT TESTED and a pointer to evidence (file, run tag, screenshot). Example: `data/audit/sneha-concerns-1-4-3.md` and the verdict table at the top of `20-sneha-next-game-2026-10-27.md`. Rule: NOT TESTED is written honestly; never count a failed script click.
2. **Read-only multi-agent audit with skeptics.** `data/audit/audit-1-4-3.md`: findings checked against the owner rules, each by 2 skeptics; result 45 confirmed, 10 refuted. First verify every item against the CURRENT commit (it may be stale), then fix only the real ones.
3. **Falsification (plant break, see red, restore).** For every fix: disable the fix, see its test fail, restore, see it pass (used throughout: `validateCfg` carry-over, 12 s override, free pack insert, once-only mark, reconnecting, report block). A test that never failed is not evidence. Same idea in `aoa-rwa/scripts/mutate.ts` + `mutations.json` (mutation checks) and in the DPDP/PROJEXA mutation runs.
4. **Independent oracles.** Rules are checked against a second implementation (sigma-steps), and winners/claims are re-read from the database, never from the success message the page showed.
5. **Mistakes register.** `docs/MISTAKES_CHECKLIST_2026-10-25.md`: each error, why, correction, status. Includes process faults (told the owner "all live" while later changes were undeployed; checked only the form I expected). Fix the process, not just the bug.
6. **Post-customer feedback.** After every real customer game record what felt better/worse (Sneha: `110-user-feedback-gap-plan-2026-10-29.md`, status words fixed-live / partly / open / "A = ask the customer").

## 4. Gap-finding method

- **Option-model enumeration.** List every choice the organizer can make and test the cross-product, not the happy path: audiences (5) x verify (4) x mode (2) x outcomes (6) x events (7) = 1,680 journeys (`gen-journeys.mjs`); live matrix of 9 games L1-L9 (`docs/LIVE_GAME_CHECKLIST_2026-10-27.md`) with expected counts per game (joined, waiting, admitted, declined, lapsed, winners).
- **Personas and roles.** Organizer, Host, Co-host, guest with invite, stranger who waits, stranger who is declined, undecided stranger, player on a second phone, player who returns after away, new e-mail vs known e-mail. Permissions family (`gen-permissions.mjs`).
- **Sneha-class patterns** (what a real first customer actually hits): step-by-step console dead ends; a file box that kills the form; copied blanks (four prizes with no text); published late for a start time; link opened on two phones; wrong e-mail at sign-in; timing doubts (9 s feels fast, 6 s after Resume); "was it really started"; report arrival time; claims confusion. Each becomes a scenario.
- **Client-twin bugs.** If the server loses a value on save, check the client form for the same loss (rows 16 and 19 of the mistakes list).
- **Reviewer fan-out.** 7 reviewers predicted 240 findings, a judge kept 217 (`110-user-feedback-gap-plan-2026-10-29.md`). Useful once per product, expensive; do not repeat per release.
- **Carry-over audit.** `docs-games/ALL_GAMES_CARRY_TAMBOLA_RULES.md`: every Tambola rule becomes a row per game: built+tested+falsified, or "not applicable because...".

## 5. Release / go-live gate

Do in this order, every release:
1. **No live game.** Run `python3 -I C:\ct\test-sites\tools\live_games_now.py 6` (read-only, counts only; games started in the last 3 h or in the next N hours). For other games: `live_games_now_game.py <D1 id> 6`. If any game is running or starts inside the window, do not deploy and do not run heavy tests.
2. **Tests green** on the commit (L1) and falsification of the fix done.
3. **Pre-deploy local check**: build (`bun run pages/build.mjs`), local click-only game passes (L5).
4. **Deploy**: Tambola `tools/browser-tests/deploy_tambola_live.ps1` (build + `wrangler pages deploy`, token from `.env.local`); other games `tools/deploy_game_live.ps1`, bingo `tools/deploy_bingo_live.ps1`. Env: only the tokens in `.env.local`, never printed or committed. Add the `releases.json` entry for every release. Do not use the `FREE_LAUNCH` switch; never switch live mode; no money.
5. **Version check**: `curl https://<site>/version.json` must show the new commit (built-at time too). Cloudflare Pages caches css/js for 4 hours: link `?v=N`, bump the service worker version on any visual change.
6. **Live 10-player check**: demo pack, real Chrome, full game with claims, then **re-read claim, winner and participant rows from D1** (read-only token) and compare with what players saw. Passed on Tambola releases 1.5.0 to 1.6.6.
7. **Push to GitHub** (retry if DNS flaps), update the handover and memory note with the live commit and what is NOT live.
8. **Rollback**: previous Pages deployment from `tools/list-deploys.mjs` / `docs/DEPLOYS.md`; for the domain move the note's rollback script. Cloudflare API gives intermittent 500s: retry with sleeps and verify state after each step. Incident record: 28 Oct 19:46-19:51 IST apex 522 for about 5 minutes.
9. **Say exactly what is live** (commit) and what is not. This was mistake 8.

## 7. What the Tambola testing did NOT cover (honest gaps)

- Never certified six sigma. Rule steps at 1M are real; number delivery to phones and per-game steps cannot be proven to 3.4 per million by sampling.
- Real 10,000 phones, and the real 1,000-player live game on corporatetambola.com, were not proven (laptop limit; free-plan request limits; cloud box cannot reach the live site).
- Real paid transactions (Rs 1 and above) and payment webhooks in live: owner-only; Razorpay window and invoices were tested in test mode; PayPal not built.
- Live Host e-mail-code sign-in could not be tested (no readable inbox); report e-mail about 3 minutes after the end and its PDF were not read end to end on the live outbox for Sneha-class games.
- Strict claim before the next number, late claim "Ohooo" message: real clicks failed in the Sneha script (hidden duplicate button), so row 8 stayed NOT TESTED; claims on the very last number (no winner rows written) were not judged; pause then full 12 s after Resume (S06) is open.
- Board and big screen claim pop-ups, away-and-return, Do Not Disturb, locked phones were not covered.
- Beacon lateness (numbers 72 and 88 came 6.7 s and 10.9 s late) is external and open; public drand answers 5xx often.
- Not run: Lighthouse, ZAP security scan, a screen reader (axe only), full permissions and full matrix families (about 160 journey scenarios skipped), second laptop path (PEHU), WhatsApp real delivery.
- Languages beyond English; real Safari on iPhone (only Playwright WebKit); real low-end Android phones; poor-network field test.
- Other games: Tic Tac Toe 1.4.0 untested, Luck by Chance not ported, Lucky Draw has no mockup, Who Knows shelved. Master console (hand-over not working, MC-01) not live. Retention after the 20 h erase not re-verified. Domain and uptime alarm PR #2188 open.
- DPDP: no guided-error live proof for every screen in the last run; Razorpay live payment untested; mail deliverability checked only for dpdp@.
- Townhall: nothing ran on the real runtime, no UI.

## 8. Token-saving rules

**Run cheaply and mechanically (low effort, no judgement; use a cheap model or plain scripts):**
- `live_games_now.py`, `curl version.json`, `bun test`, `sigma-steps.mjs`, `sim2/smoke.mjs`, `list-deploys.mjs`, status polling.
- Read only tails: `tail`, `grep -c`, the `*.summary` / `*.json` result files (`data/ui/live-matrix.summary`, `data/sigma-steps.json`), never whole logs.
- Re-running a scenario already proven green on the same commit: skip.
- Generated matrices (`gen-*.mjs`) and the 9 assertions are fixed lists: script the check, do not ask a model to eyeball.
- Let a scheduled job do waiting: an every-15-minute self-resume and a 5-minute network retry (owner rules), not a model polling.

**Needs judgement (medium or high effort):**
- Reading what a failure means (test flaw vs product bug vs laptop load vs external beacon). Medium.
- Option-model design for a new game, wording review for readers with low literacy, claim/late rules, go/no-go for live. High.
- The audit with skeptics and the owner-concern table: once per product, then only on changed areas. High, but bounded.
- Anything touching money, privacy text, legal wording, or mode switches: ask the owner.

**Avoid repeating:**
- Do not re-run the whole 100-case campaign or 1M steps after a small fix: rerun the one scenario that failed plus its falsification.
- Do not build ad-hoc scripts: reuse `ui-game.mjs`, `campaign.mjs`, `live.mjs`; copies of old `dbg*.mjs` and `patch_*.py` in `tools/` are throwaway.
- Do not re-audit with seven reviewers per release; use the existing `110-...` list and tick items.
- Do not test via API what a person clicks (the biggest bugs hid there).
- Do not run heavy tests on the laptop while a live game or another heavy job runs; wait for the lock and RAM.
- Do not paste secrets or long logs into chat; do not use `git show X > file` or large heredocs in this shell (output filter corrupts them; use the Write tool or Python bytes; `wb` mode to avoid CRLF).
- Do not use the stale `tools/make-legal-pages.mjs` (refuses to run on purpose).
- One heavy job at a time (RAM about 700 MB free on this laptop); use cloud sessions for L1, L2, L4 (local server) and L7 in-process, the laptop only for L5 and L6.
