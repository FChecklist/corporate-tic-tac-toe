## The console Pay step (see `docs/CONSOLE_PAY_STEP.md`)
- The contract itself lives in the console repository (`docs/GAME_PAY_CONTRACT.md`); it is not copied here. What is here: the vendored bridge and contract kit (`apps/edge/src/console-bridge/`, `apps/edge/test/console-contract/`) and the game's side (`apps/edge/src/console-adapter.ts`).
- `payInfo`: read only, `owner` is true only for an organizer account of the game's own org. `markPaid`: repeatable by the SAME order (a different order on an already paid game is a definite refusal; records are written only when this call did the unlock, via `changes()`); owner and size checked again; a wrong owner, wrong size, closed game or the free size is a definite refusal; an already paid game changes nothing; unlock (`engagement.pack`) and records land in one batch.
- A game is marked paid only through the console's signed notice (`/api/console/paid`): the signed assertion is single use (`console_jti`), lives at most 60 seconds, is tied to the game, and each order id is taken once (`console_paid`, migration 0033; it was 0031 before the live merge, because live uses 0030 and 0031).
- Known limit, for the console side: the signed assertion is bound to the game and the person, not to the order id or size; those travel in the request body. Only the console can sign, so this is not exploitable from outside, but the console may want to bind them.

## One-game console key (version 1.4.2)
- The key the console hands over for one game lives in `sessionStorage` under its OWN name, `cbz-game-key`, in that tab only. It is never written under `cbz-org` (keep.js copies that name into `localStorage`, and prefers what is already there). `zc.js` reads it from `sessionStorage` only, removes any lasting `cbz-org` / `cbz-alt` on the device, and neither offers nor takes a key through the other-tab channel. Sign out calls `POST /api/console/signout`, then clears the tab. Tests: `apps/web/test/console-handoff.test.ts`.
- Other pages opened from there in a new tab (`pay.js`, `preview.js`) read the lasting store, which is now empty: they ask for a sign-in. Accepted for now.

## "ID matched, not proven" (owner decision, accepted)
- An employee ID (and a typed mobile number) is MATCHED to the organizer's list. It is not proven: anyone who knows a listed ID can type it. The personal link (and the e-mail code for organizers) is the strong proof. The owner accepted this and decided there are NO per-address limits on right IDs (wrong IDs are still limited per address). The help in `zc.js` says so (one sentence under "Who can join", since the four choices are gone); a test keeps it. `docs/SUITE_RULES.md` (the suite's rules file) is not in this repo.
- Old lists: before 1.4.1 an ID was kept with its dashes (`E-101`). Since 1.6.0 `migrateEmpAliases` (`people.ts`) reads each listed person's stored ID once per game and points today's reading (`E101`) at the old hash, so `E-101`, `E 101`, `E/101` and `e101` all find that person on an old list. See "The invite rule (version 1.6.0)".

## Per-address limits and erasing console data (version 1.5.1)
- Every limit that counts tries per internet address uses `netKeyOf(req)` (`apps/edge/src/netkey.ts`): IPv4 as it is, IPv6 by its first 64 bits (the /64). Never hash `cf-connecting-ip` directly for a counter. This is what keeps "wrong IDs are limited per address" true for IPv6, which "ID matched, not proven" relies on. Stored analytics and audit rows still keep their own shortened address; they are not counters.
- `erasePersonal` (`apps/edge/src/lifecycle.ts`) deletes, per game and on its own after the atomic batch: `game_role` (Host / Co-host roles with the sealed e-mail), `console_handoff` (unopened links) and revokes the console keys of that game. Each step ignores a missing table, so a database without the bridge never blocks deleting people. Test: `apps/edge/test/stage-log-erase.test.ts`. `endRoles` in the bridge is still not called anywhere on purpose: the erase path above covers it.
- `cpaid/<game>` (the console order reference) is kept after erasure on purpose: it is a payment record the law keeps.
- Help (`guide.js`, "This sign-in is for one game only") says that opening a game from your console signs you out of any other sign-in saved on the device.
- The live site's `/version.json` could not be read from the build box on 23 Nov 2026 (network block); the live commit used is `fa5ab0afa895`, from the earlier merge note. Re-check it against the live site before the owner deploys.

## The invite rule (version 1.6.0)
Owner words, 23 Nov 2026, for every game that comes in through console.corporatetambola.com. Where it lives in this repo:
1. **One game link for everybody.** Nothing changed here; the common link is the only link a guest needs. Personal links (`/j/<token>`) still exist for people an organizer lists by mobile number.
2. **An ID on the organizer's list lets the person in, no approval.** `join` in `worker.ts` (`personByEmp`). Wrong IDs are still limited per network (`idmiss/`, `netKeyOf`), 30 per 10 minutes.
3. **No ID, or an ID not on the list: name, mobile number and e-mail go to the organizer or a Host.** The join answers `400 need-contact` until all three are given and valid, then `403 waiting` and a request in the waiting room (`addWaiting`, `waiting.pii` carries name, mobile, e-mail and the ID that was typed). `listWaiting` shows the full request to the Organizer and Hosts only (`who.all`); a Co-host or a guest who owns a link sees first name and last four digits, never the e-mail. A mobile number on a list is no way in by itself: the person asks, or uses a personal link. After a yes the same request is sent again and the person is let in (`admittedBefore`).
4. **The ID is one alphanumeric field.** `VERIFY_MODES` is `["id"]` (`packages/beacon/src/config.ts`): `mobile`, `either` and `both` are refused when saved (400) and read as the one rule in a game saved earlier. `verifyOf` (`people.ts`) has no mode, only `employeesOnly` and `idKind`. The console (`zc.js`) no longer shows the four choices (nor the Employee / Email ID choice). Every ID is cleaned the same way at upload, join, approval and matching: letters and numbers only, capitals (`A-1101` = `A 1101` = `A/1101`). `EMP_CLEAN_FROM_MS` is 0 so this is in force for every game.
   - **Lists made before 1.6.0:** they hold hashes of the old reading (`E-101`). `migrateEmpAliases` runs once per game the first time an ID is looked at or uploaded: for each listed person whose stored ID has more than letters and numbers it writes one pointer `idx/<game>/<hash of E101>` to the old hash. No person is rewritten. The old reading (`legacyEmpHashOf`) is still tried too. An empty list is looked at again next time. Tests: `invite-rule.test.ts` ("a list made before this version"), `verify.test.ts`.
5. **The list and all IDs are deleted within 24 hours after the game ends.** Already true: `personalDeleteAt = end + 20 hours` (`lifecycle.ts`), and `erasePersonal` deletes people, the waiting room (with its e-mails), seats, participants, the ID pointers (`idx/<game>/`) and, since 1.6.0, the migration note (`empmig/<game>`). Kept true by `invite-rule.test.ts` (rule 5).
- **Where the rule applies:** a game by invitation (a list game, `closed`). A game that anyone with the link may join (made before, or through the API, `closed = 0`) keeps its name-only join, because it has no list to check an ID against. The console does not make those any more by default but still has the "Anyone with the link" tap; the page learns which kind it is from `byInvite` in `/info`. Decision for the owner: remove that tap too if every game must ask for an ID.
- **Notice wording:** the join notice (`consent-text.json` K4 box A, and `consent.js`) now says the e-mail is asked, shown only to the organizer and hosts, and deleted at the same time. The Terms version `2026-11-01` was NOT changed. Owner or legal to decide whether the notice needs a new version date. The data map (`docs/PRIVACY_AND_LIFECYCLE.md`) lists the e-mail.
- **ID kind lock:** once anyone is listed or has joined, the ID kind (Employee ID or Email ID) cannot change (409 `id-kind-locked`); before 1.6.0 a game listed only by mobile number could still change it.
- **Per-address limit, funnel:** `funnel.ts` now counts the page beacon per `netKeyOf(req)` like every other limit.
- `bun.lock` is tracked in this PR (new on `master`). `@types/bun` is pinned to `latest` there.
- Help: `guide.js` has an entry for "No ID, or not on the list" (the `need-contact` answers) and the console sign-in help line "Opening a game from your console signs you out of any other sign-in saved on this device." now has its own test (`guide.test.ts`).
